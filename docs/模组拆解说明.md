# 模组拆解说明（Module Pack Format v2）

> 版本：v1.1（2026-09-01）
> 用途：把 **PDF / 文本+图片** 混合的模组源材料，拆解为项目可读取的结构化模组包，供 AI 守密人按需读取。

---

## 1. 设计目标

1. **AI 可读**：模组内容按「开局注入 / 场景注入 / 运行时 KP 上下文 / 按需检索」组织（见 §4），AI 守密人不需要通读全文就能正确调度。
2. **隐私分级**：玩家可见内容（`plot.md` 与 `scenes.json` 的表侧字段：`name` / `location` / `intro` / `handouts`）与守密人真相（`kp-notes.md` 及 `scenes.json` 的 `summary` / `checks` / `clues` / `npcs` 等字段）物理分离，后者只进 AI 上下文；玩家接口与广播只发投影（见 §3.6 程序契约）。
3. **图片可管理**：PDF 里的插图 / 地图 / 立绘拆出为 `handouts/` 图片，在 `scenes.json` 中声明"何时展示、给谁看"。
4. **可校验**：拆解产物有明确 schema 与校验清单（§6），AI 或人工都能检查完整性。

## 2. 目录结构

```
modules/<module_id>/
├── meta.json          # 元数据（schema: trpg-module/v1）
├── plot.md            # PL 视角剧本（背景 / 开场 / 场景 / 结局）
├── kp-notes.md        # 守密人真相（只进 AI 上下文，绝不进玩家视图）
├── clues.md           # 线索表（- [ ] **C-XX** 格式，参见 §3.4）
├── npcs.json          # NPC 条目（可选，程序当前不读取，参见 §3.5）
├── monsters.json      # 怪物条目（可选，程序当前不读取，参见 §3.5）
├── scenes.json        # ★ 场景结构化（场景清单 + 字段，参见 §3.6）
├── pregens/           # 预制角色（角色卡 JSON，见 §3.8）
├── handouts/          # 图片附件（按用途分子目录，参见 §3.7）
└── README.md          # 可选：来源 / 授权条款 / 拆解备注
```

## 3. 文件规范

### 3.1 `meta.json`（schema: `trpg-module/v1`）

完整示例：

```json
{
  "schema": "trpg-module/v1",
  "id": "the-haunting",
  "number": 1,
  "name": "The Haunting",
  "cn": "惊魂",
  "author": "Chaosium",
  "language": "zh-CN",
  "system": "coc7",
  "players": "1-2",
  "duration": "2-3 小时",
  "recommended_skills": ["侦查", "倾听", "魅惑", "急救"],
  "tags": ["官方短模组", "1920 年代", "波士顿", "鬼屋", "经典入门"],
  "summary": "……（KP 视角剧情梗概，可含真相与通关路线）",
  "public_summary": "……（无剧透的玩家可见简介：只交代钩子与氛围，内容页展示）",
  "background": {"year": "1920", "location": "美国 波士顿 Cambridge 区 Bouverie 街 18 号"},
  "source": {
    "type": "pdf",
    "file": "the-haunting.pdf",
    "pages": 32,
    "notes": "原版 PDF 等源材料不放入模组包"
  },
  "scene_flow": ["s01", "s02", "s03"],
  "files": {
    "plot": "plot.md",
    "kp_notes": "kp-notes.md",
    "clues": "clues.md",
    "npcs": "npcs.json",
    "monsters": "monsters.json",
    "scenes": "scenes.json",
    "pregens": "pregens/",
    "handouts": "handouts/"
  }
}
```

字段细则：

| 字段 | 必填 | 说明 |
|---|---|---|
| `schema` | ✅ | 固定 `"trpg-module/v1"`（程序按此识别模组） |
| `id` | ✅ | 模组目录名（全小写连字符，如 `the-haunting`） |
| `number` | ✅ | 整数序号，新模组取现有最大值 +1 |
| `cn` | ✅ | 中文名 |
| `system` | ✅ | 本期固定 `"coc7"` |
| `summary` | ✅ | 剧情梗概。**KP 视角**（含剧情走向/结局）：玩家可见接口一律不下发 |
| `files` | ✅ | 各文件/目录的声明（路径相对于模组目录）；`files` 中声明的每一项必须真实存在 |
| `name` | — | 英文原名 |
| `author` / `language` | — | 作者 / 语言 |
| `players` / `duration` | — | 人数 / 时长（前端展示） |
| `recommended_skills` / `tags` | — | 推荐技能 / 标签。**`tags` 为 KP 视角**（可能含怪物/世界观关键词），玩家接口不下发 |
| `background` | — | 年份 / 地点 |
| **`public_summary`** | ✅（程序校验） | **无剧透的玩家可见简介**（内容页 / 模组列表展示）。写作要求：只交代钩子与氛围（"为什么来"），不出现怪物名、真相、通关目标、结局走向。缺失时 `validate_module` 报错、平台对玩家展示"剧情简介对玩家保密"占位 |
| `source` | — | 源材料信息（类型 / 文件名 / 页数 / 备注）。**KP 视角**，玩家接口不下发 |
| `scene_flow` | — | 场景顺序（`scenes.json` 的 id 列表）。**推荐必填**：程序按此排序场景、取第一项为开局场景 |

### 3.2 `plot.md`（PL 视角剧本）

玩家可看内容的完整剧本。**只允许出现玩家最终能知道的信息**；守密人调度提示用 `> 🔒 守密人：` 引用块标注（AI 读取时识别这类提示，不输出给玩家）。

结构（按此顺序组织）：

```markdown
# <模组名> · 玩家剧本

## 1. 背景
<世界设定、起始处境、玩家角色设定（一两段）>

## 2. 开场
<守密人开场朗读文本——开团时原样读给玩家的一段文字>

## 3. 场景清单
| 场景 | 名称 | 地点 | 触发条件 | 概要 |
|---|---|---|---|---|
| s01 | 抵达园区 | 秋林苑门口 | 开场进入 | 出租车驶入、保安室 |

## 4. 场景详情
### s01 抵达园区
<场景的完整描述文本（玩家能看到的部分），可长可短>
- 可检定点：<可选，与 scenes.json 的 checks 呼应>
- 🔒 守密人：<只进 AI 上下文的调度提示，绝不输出>

### s02 ……（其余场景同构）

## 5. 结局
<各结局的达成条件与结局文本>
```

### 3.3 `kp-notes.md`（守密人真相）

只进 AI 上下文的全部真相。**任何情况下不进入玩家视图**（服务端过滤层保证：建团时全文写入该局 `kp_notes` 表，每轮管线注入守密人上下文）。

结构：

```markdown
# <模组名> · 守密人真相（仅 AI 上下文，绝不进玩家视图）

## 1. 真相
<事件全貌：发生了什么、元凶是谁、动机、世界真相>

## 2. NPC 隐藏面
<每个 NPC 的隐藏身份 / 动机 / 真实能力 / 玩家视角与之的差异>

## 3. 未揭示线索
<每条线索：编号、触发条件、玩家会发现什么、AI 何时让线索生效>

## 4. 失败预案
<玩家关键检定失败 / 作死 / 团灭后的剧情走向与兜底>

## 5. 数值参考
<怪物 / NPC 的战斗数值、理智损失表（如需）>
```

### 3.4 `clues.md`（线索表）

程序解析格式（`- [ ] **C-XX** 线索正文…`，必须逐字对齐）：

```markdown
# 《模组名》线索表

- [ ] **C-01** Coswick 的来信（开场）：「速来 Cambridge 区，Bouverie 街 18 号。有事相商。」——触发玩家行动
- [x] **C-02** Coswick 本人（虚弱苍白）：「夜里被一只看不见的手掐着醒来。」
```

规则：

- 每条目一行起始：`-`（或 `*`）+ 空格 + `[ ]`（未发现）或 `[x]`（已发现）+ 空格 + `**C-XX**`（粗体编号）+ 空格 + 正文。
- 编号：`C-01`（推荐）或 `C01`；编号供线索台账与「获得/解锁」引用，同一模组内唯一。
- 条目边界：正文延续到**下一个条目行**或 **`#`（1–6 级）标题行**或文末。标题行（如 `## 三楼 A 室`）可用来分组，不会被并入任何条目。
- 一条线索的补充信息（触发条件 / 私密标记 / 关联场景与 NPC）可直接写在正文中（多行保留换行）。
- 文件头可用 `#` 标题与引用块说明（不参与解析）。
- 程序行为：建团时解析生成每局线索台账副本；获得线索经 `state_apply` 解锁并记录时间与获得者；每轮管线把台账格式化为 `[C-01] [已获得] 文案…` 注入守密人上下文（KP 视角，绝不进玩家视图）。

### 3.5 `npcs.json` / `monsters.json`（可选）

每条目结构：

```json
{
  "id": "shen-kecheng",
  "name": "沈珂成",
  "public": {"appearance": "俊朗年轻人，挽起袖子", "behavior": "热情好客", "lines": ["等你很久了。"]},
  "hidden": {"true_identity": "谢尔顿的伪装", "stats": {"STR": 60}}
}
```

- `public`：玩家可看信息（外貌 / 举止 / 台词）。
- `hidden`：只进 AI 上下文的信息（真实身份 / 数值）。

> **程序现状**：这两个文件**当前不被程序读取**，仅作拆解归档。AI 运行时获得的 NPC / 怪物信息来自：① `scenes.json` 场景的 `npcs` / `monsters` 数组（随场景对象整体注入 AI 上下文）；② `kp-notes.md` 的「NPC 隐藏面 / 数值参考」（§3.3）。拆解时应提供本文件，内容与场景条目、kp-notes 保持一致；影响 AI 判定的关键信息以场景条目与 kp-notes 为准。

### 3.6 `scenes.json`

```json
{
  "scenes": [
    {
      "id": "s01",
      "name": "抵达园区",
      "location": "秋林苑门口",
      "intro": "……（玩家可见入场白：为什么来 / 怎么来的 / 现在在哪，写作规范见下）",
      "summary": "出租车驶入，铁艺大门，保安室，原木色别墅",
      "checks": [
        {"kind": "skill", "skill": "知识", "target": 50, "note": "建筑风格"},
        {"kind": "sanity", "loss": 1, "note": "直面怪异现象"}
      ],
      "clues": ["C-01"],
      "npcs": ["shen-kecheng"],
      "handouts": ["cover.jpeg", "maps/qiulin-court-map.jpeg"],
      "next": ["s02"]
    }
  ]
}
```

字段细则：

| 字段 | 必填 | 说明 |
|---|---|---|
| `scenes` | ✅ | 场景数组；每个场景必须含 `id` |
| `id` | ✅ | 场景唯一标识（如 `s01`），与 `meta.scene_flow` 对应 |
| `name` | — | 场景名（场景切换也可按 name 匹配；推荐填写）。**玩家可见**（场景栏 / 场景消息展示当前场景名）：命名必须表侧化——用玩家当前能感知的地标/事件词，**禁止**出现怪物名、机制词、结局词（反例：`冷蛛袭来 / 石像归位`；正例：`石像归位` 只在玩家已拿到石像的场景使用） |
| `location` | — | 地点描述。**玩家可见**（同上） |
| **`intro`** | ✅（程序校验） | **玩家可见的场景入场白**。开局注入的首场景 `intro` 就是玩家看到的开场白；场景切换时随 `scene_changed` 展示。缺失时 `validate_module` 报错。写作要求见下方「intro 写作规范」 |
| `summary` | — | 场景概要。**KP 视角**（含怪物身份、检定安排、SAN 损失、后续走向）：只进 AI 守密人上下文，玩家接口与广播一律不下发 |
| `checks` | — | 场景检定提示数组：`kind` 为 `skill`（配 `skill`+`target`）/ `sanity`（配 `loss`）/ `luck`；`note` 为说明。供裁判阶段 AI 参考，不强制 |
| `clues` | — | 本场景关联线索编号（对应 clues.md 的 C-XX） |
| `npcs` / `monsters` | — | 本场景出现的 NPC / 怪物 id 列表 |
| `handouts` | — | 附件相对路径（对应 handouts/ 下文件） |
| `next` | — | 后继场景 id 列表（供 AI 调度参考，程序不强制） |

intro 写作规范（玩家可见，逐条自检）：

1. **交代三件事**：调查员**为什么来**（钩子：一封信 / 一条短信 / 一个约定）、**怎么来的**（交通 / 缘由）、**现在在哪、正发生什么**（可直接感知的景象/声音）。
2. **只写玩家能感知的**：可描写看到的、听到的、闻到的；**禁止**出现怪物真名、身份归属（如"不明黑色物体（筑巢冷蛛的腹部）"→ 只写"不明黑色物体"）、检定名与目标值、SAN 数值、未触发的后果、后续场景走向。
3. **收在可行动的状态**：结尾留给玩家一个可以回应的局面（雾更浓了 / 有动静 / 车门没开），不要替玩家做决定或宣布检定。
4. **长度**：建议 100–300 字，第二人称（"你们"）。

程序契约：

- 场景排序：按 `meta.scene_flow` 顺序返回；未列入 flow 的场景补在末尾；`scene_flow` 为空则按文件原序。
- 开局：取 `scene_flow[0]`（或 scenes[0]）为首场景，生成玩家可见的开场 scene 消息并设为 `current_scene`。开场白 = `intro`（缺失时仅「场景名 · 地点」表头，**绝不回退到 summary**）；首场景 `handouts`（玩家资料）同时以 handout 消息注入叙事流。
- 注入：每轮管线把**当前场景对象整体**（以上全部字段及任意自定义字段）注入裁判与叙事阶段的 AI 上下文——AI（KP）始终读全量，投影只发生在玩家边界。
- 切换：按场景 `id` 或 `name` 查找。
- **玩家边界投影**：`/api/modules/{id}`、`/api/modules` 剥除 meta 的 `summary` / `tags` / `source`；`/api/modules/{id}/scenes` 与 `scene_changed` 广播只含 `id / name / location / intro / handouts`。`summary` / `checks` / `clues` / `npcs` / `next` 绝不离开服务端（供 AI 使用）。

### 3.7 `handouts/`（图片附件）

```
handouts/
├── cover/        # 封面 / 氛围图
├── portraits/    # 角色立绘（NPC / 玩家）
├── maps/         # 地图（园区 / 楼层 / 区域）
├── items/        # 道具图（信件 / 符咒 / 机关）
└── kp-tips/      # 守密人提示图（只进 AI 上下文，不展示给玩家）
```

- 格式：jpg / png / webp，单张 ≤ 10MB；子目录可自定义（`scenes.json` 的 `handouts` 引用相对路径，如 `maps/qiulin-court-map.jpeg`）。
- 每张图在 `scenes.json`（或 `meta.json`）中声明用途（何时展示、给谁看）。
- 服务端经 `/api/modules/{id}/handouts/{路径}` 返回，越界/缺失返回 404。

### 3.8 `pregens/`（预制角色）

每张调查员一张 JSON 文件（文件名即角色标识，如 `theron-quist.json`），schema `coc7-character/v1`。程序读取目录下全部 `*.json`，在前端角色页展示并支持一键使用。

完整示例：

```json
{
  "schema": "coc7-character/v1",
  "name": "塞隆·奎斯特",
  "cn": "Theron Quist",
  "meta": {
    "age": 38,
    "occupation": "医生",
    "background": "一战时任医疗官，与委托人是大学同窗"
  },
  "attributes": {
    "STR": 50, "CON": 60, "SIZ": 55, "DEX": 55,
    "APP": 60, "INT": 75, "POW": 65, "EDU": 80, "LUK": 55
  },
  "derived": {
    "HP": 12, "MP": 13, "SAN": 65, "DB": "0", "MOV": 8
  },
  "skills": {
    "First Aid": 60, "Medicine": 30, "Psychology": 80,
    "Spot Hidden": 50, "Library Use": 45, "Listen": 45,
    "Dodge": 35, "Charm": 35, "Persuade": 45, "Language(English)": 65
  },
  "inventory": ["医用手提包", "手电筒", "笔记本"],
  "notes": ["一战时任医疗官，曾目睹壕沟战的恐怖"],
  "sanity": {"current": 65, "max": 65, "history": []}
}
```

字段细则：

| 字段 | 必填 | 说明 |
|---|---|---|
| `schema` | ✅ | 固定 `"coc7-character/v1"` |
| `name` | ✅ | 角色名 |
| `cn` | — | 别名 / 外文名 |
| `meta` | — | `age` 年龄、`occupation` 职业、`background` 背景（自由扩展） |
| `attributes` | ✅ | 九项属性：`STR / CON / SIZ / DEX / APP / INT / POW / EDU / LUK`，百分制 3–99 |
| `derived` | ✅ | 五项派生值，公式见下 |
| `skills` | ✅ | 技能表：**英文技能名 → 数值（0–99）**，如 `"Spot Hidden": 50` |
| `inventory` / `notes` | — | 物品字符串列表 / 角色笔记列表 |
| `sanity` | — | `{current, max, history: []}`；缺省时程序取 `derived.SAN` |
| `state` | — | 可变状态段，可整段省略（程序自动补全） |

派生公式（与引擎一致，必须与 `attributes` 自洽）：

- `HP` = ⌈(CON + SIZ) / 10⌉
- `MP` = ⌈POW / 5⌉
- `SAN` = **POW**（初始理智等于意志值本身，不要乘 5）
- `DB`：按 STR + SIZ 查表——≤64 → `"-2"`；≤84 → `"-1"`；≤124 → `"0"`；≤164 → `"+1d4"`；≤204 → `"+1d6"`；更大 → `"+2d6"`
- `MOV` = 8；STR < DEX 且 STR < 80 时 −1；SIZ > 79 时 −1（最低 1）

`sanity.current` / `sanity.max` 均等于 `derived.SAN`。技能键用英文（平台技能表以英文为准）。

## 4. AI 读取模式

| 模式 | 内容 | 时机 |
|---|---|---|
| **开局注入** | ① `scenes.json` 首场景 → 玩家可见开场消息（`intro`，无 intro 则仅表头）+ 首场景 `handouts` → 玩家资料手卡消息；② `current_scene`；③ `kp-notes.md` **全文** → 该局 `kp_notes` 表（round 0）；④ `clues.md` → 线索台账副本 | 创建游戏 / 开局 |
| **场景注入** | `scenes.json` 当前场景对象**整体** → 裁判与叙事阶段 AI 上下文 | 每轮管线 |
| **运行时 KP 上下文** | `kp_notes` 表尾部（开局原文 + 每轮 `private_notes`）+ 线索台账文本（`[C-01] [已获得/未获得] 文案…`）→ AI 上下文 | 每轮管线 |
| **按需检索** | `pregens/`（建卡页展示与一键使用）、`handouts/`（场景附件渲染于叙事流） | 运行时按需 |
| **不注入** | `plot.md`、`npcs.json`、`monsters.json`（不参与运行时注入，作用见 §3.2/§3.5） | — |

> 所有 KP 侧内容（kp_notes 表 / 线索台账 / private_notes）只进 AI 上下文，绝不进玩家视图（SSE 公共流、公共视图、消息表均不含）。

## 5. 拆解步骤

1. **通读源材料**（PDF / 文本+图片），识别：背景、场景流程、检定、线索、NPC、怪物、附件图片。
2. **建目录**：`modules/<id>/`（id 全小写连字符）。
3. **分文件**：按 §3 规范写入 `plot.md` / `kp-notes.md` / `clues.md` / `npcs.json` / `monsters.json` / `scenes.json` / `meta.json`。
4. **图片分类**：从源材料提取插图，按用途放入 `handouts/` 分类目录（jpg/png/webp，≤ 10MB）。
5. **预制角色**：如有官方/推荐调查员，按 §3.8 角色卡格式转 JSON 放入 `pregens/`。
6. **登记编号**：`meta.json` 的 `number` 取现有模组最大值 +1。
7. **校验**：跑 §6 校验清单。放回 `modules/` 后由 `/api/modules` 自动收录（扫描目录即可见）。

## 6. 校验清单

> 标 🤖 的条目由 `server.modules.validate_module` **自动校验**（`modules.validate_module(id)` 逐项报错；pytest `test_all_modules_pass_validation` 对全部已发布模组长期看护）——新模组入库前必须过它，其余条目为人工检查。

- [ ] 🤖 `meta.json` 合法 JSON，`schema == "trpg-module/v1"`，必填字段齐全（id / number / cn / system / summary / files）
- [ ] 🤖 `files` 中声明的每一项（文件/目录）实际存在
- [ ] `plot.md` / `kp-notes.md` / `clues.md` 为 UTF-8 Markdown
- [ ] `clues.md` 每条目为 `- [ ] **C-XX** 线索正文…` 格式（编号在模组内唯一）
- [ ] 🤖 `scenes.json` 为 `{"scenes": [...]}`，每个场景含 `id`；`meta.scene_flow` 中的 id 均存在于 scenes
- [ ] 🤖 每个场景含非空 `intro`（玩家可见入场白，按「intro 写作规范」四条自检）
- [ ] 🤖 `meta.json` 含非空 `public_summary`（无剧透简介）
- [ ] 🤖 场景 `handouts` 引用的每一张图真实存在
- [ ] `npcs.json` / `monsters.json` / `plot.md`（如提供）为合法 UTF-8 JSON/Markdown
- [ ] `handouts/` 图片格式合法（jpg/png/webp），`scenes.json` 引用的附件真实存在
- [ ] `pregens/` 每张角色卡为合法 JSON，`schema == "coc7-character/v1"`，含 `attributes` / `derived` / `skills`，派生值与属性自洽（`SAN == POW`）
- [ ] `kp-notes.md` 与 `plot.md` 无交叉泄漏（真相只出现在 kp-notes）
- [ ] `public_summary` 内容无剧透（不出现怪物名 / 真相 / 通关目标 / 结局；程序只校验存在性，内容靠人工）
- [ ] `intro` 内容过 intro 写作规范四条自检（程序只校验存在性，内容靠人工）
- [ ] 场景 `name` / `location` 表侧化：不含怪物真名、检定名、SAN 数值、结局词
- [ ] **玩家视角通读**：把 `/api/modules/{id}/scenes` 的返回和开场消息当作玩家能看到的一切——任何一条"未揭示信息"出现在其中即不合格
- [ ] 源材料（原版 PDF 等）不放入模组包；模组包内只放拆解产物

## 8. 世界书

当前不开发世界书，本节仅预留格式。若未来启用，按本格式拆出独立的世界书包（与模组包分离），服务端读取逻辑与模组一致（扫描目录 → 结构化 JSON → 按关键词注入 LLM 上下文）。

### 8.1 目录与格式

```
worlds/<world_id>/
├── meta.json          # schema: trpg-world/v1 → id/name/cn/system/summary/tags/files
├── npcs.json          # NPC 条目（id / 关键词 / public / hidden）
├── locations.json     # 地点条目（id / 关键词 / 描述 / handouts）
├── items.json         # 物品条目（id / 关键词 / 效果）
├── events.json        # 事件条目（id / 关键词 / 触发 / 后果）
└── readme.md          # 来源与授权（可选）
```

每条目统一结构（关键词驱动注入）：

```json
{
  "id": "npc-shen-kecheng",
  "name": "沈珂成",
  "keywords": ["沈珂成", "房东", "表哥"],
  "tags": ["npc", "主线"],
  "public": {"appearance": "俊朗年轻人，挽起袖子", "behavior": "热情好客", "lines": ["等你很久了。"]},
  "hidden": {"true_identity": "谢尔顿的伪装", "stats": {"STR": 60}}
}
```

### 8.2 阅读逻辑

1. **开局注入**：meta 摘要 + 全部 `public` 字段（世界基调）/ `hidden` 只进 KP 上下文。
2. **按需检索**：叙事/裁判阶段按当前文本关键词命中条目 → public 进玩家视图、hidden 进 KP 上下文；未命中不注入。
3. **隐私分级**：与模组一致——`hidden` 绝不进玩家视图；kp-only 内容只进 KP 上下文。
