# 模组拆解说明（Module Pack Format v2）

> 版本：**v1.1（2026-09-01 对照 `server/modules.py`、`gm/pipeline.py`、`api/games.py` 开局注入逐条核对修订）**｜ 初版 v0.1 草案：2026-08-31
> 用途：把 **PDF / 文本+图片混合** 的模组源材料，拆解为项目可读取的结构化模组包，供 AI 守密人按需读取。
> 参考：`archive/coc7th-keeper-feishu/.dsh/skills/coc7th-keeper/modules/toy-dancer-comes/`（coc7-module/v1 拆解方式），本格式为其升级版。
> **程序契约**：§3 字段为程序实际读取/注入的契约；§4 为 2026-09-01 对照实测修订后的真实注入行为。

---

## 1. 设计目标

1. **AI 可读**：模组内容按"开局注入 / 场景注入 / 按需检索"三种模式组织，AI 守密人不需要通读全文就能正确调度。
2. **隐私分级**：PL 视角内容（`plot.md`）与守密人真相（`kp-notes.md`）物理分离，玩家视图永不接触后者。
3. **图片可管理**：PDF 里的插图 / 地图 / 立绘拆出为 `handouts/` 分类图片，声明"何时展示、给谁看"。
4. **可校验**：拆解产物有明确 schema 与校验清单，AI 或人工都能检查完整性。

## 2. 目录结构

```
modules/<module_id>/
├── meta.json          # 元数据（schema: trpg-module/v1）
├── plot.md            # PL 视角剧本（背景 / 开场 / 场景 / 检定 / 结局）
├── kp-notes.md        # 守密人真相（只进 AI 上下文，绝不进玩家视图）
├── clues.md           # 线索表（编号 / 触发条件 / 内容 / 私密标记）
├── npcs.json          # NPC（公开字段 + 隐藏字段）
├── monsters.json      # 怪物（公开字段 + 隐藏字段）
├── scenes.json        # ★ 场景结构化（场景 ID / 描述 / 检定 / 线索 / NPC / 附件引用 / 顺序）
├── pregens/           # 预制角色（JSON，schema 同角色卡）
├── handouts/          # 图片附件（按用途分类，见 §3.7）
└── README.md          # 可选：来源 / 授权条款 / 拆解备注
```

## 3. 文件规范

### 3.1 `meta.json`（schema: `trpg-module/v1`）

```json
{
  "schema": "trpg-module/v1",
  "id": "toy-dancer-comes",
  "number": 2,
  "name": "Toy Dancer Comes",
  "cn": "玩具跳着舞蹈来",
  "author": "Yukishiro",
  "language": "zh-CN",
  "system": "coc7",                    // 本期仅 coc7；dnd5e 后续
  "players": "1",
  "duration": "3-4 小时",
  "recommended_skills": ["侦查", "图书馆使用", "战斗类技能"],
  "tags": ["克苏鲁神话", "日系恐怖", "单 PL 友好"],
  "summary": "……",
  "background": {"year": "2012", "location": "松寒市 秋林苑 7 号楼"},
  "source": {                          // ★ 源材料信息（拆解溯源）
    "type": "pdf",                     // pdf | text | text_image_mixed
    "file": "玩具跳着舞蹈来.pdf",
    "pages": 42,
    "notes": "原版 PDF 存放于 archive/模组/，不入库"
  },
  "scene_flow": ["s01", "s02", "s03"], // ★ 场景顺序（对应 scenes.json 的 id）
  "files": {
    "plot": "plot.md",
    "kp_notes": "kp-notes.md",
    "clues": "clues.md",
    "npcs": "npcs.json",
    "monsters": "monsters.json",
    "scenes": "scenes.json",
    "pregens": "pregens/",
    "handouts": "handouts/"
  }
}
```

### 3.2 `plot.md`（PL 视角剧本）

沿用 toy-dancer-comes 的写法：背景 → 开场（守密人朗读）→ 关键场景表 → 各场景细节 → 结局。**只含玩家可看内容**；守密人调度提示用 `> 🔒 守密人：` 引用块标注（AI 读取时识别，不输出给玩家）。

> ⚠️ **程序现状（v1.1 核对）**：`plot.md` **当前不被程序读取/注入运行时上下文**，仅为拆解素材与人工参考（模组作者用它生成 `scenes.json` 的摘要/检定信息）。若未来需要「剧本全文注入」，可在管线中追加（预留扩展点，不需要改模组格式）。

### 3.3 `kp-notes.md`（守密人真相）

只进 AI 上下文。含：真相、NPC 隐藏动机、未揭示线索、失败后果预案。**任何情况下不进入玩家视图**（服务端过滤层保证）。

> **程序现状（v1.1 核对）**：建团时 `_inject_opening` 把 kp-notes.md **全文**写入该局 `kp_notes` 表（round 0，开局注入）；此后每轮管线的裁判/叙事阶段把 `kp_notes` 表**尾部**（最近 10 条）注入守密人上下文（`prompts.py` 的 `kp_notes_tail`）。kp_notes 绝不进玩家视图/SSE 公共流。

### 3.4 `clues.md`（线索表）

**程序实际解析格式**（`server/modules.py::list_clues` 正则提取，必须逐字对齐）：

```markdown
- [ ] **C-01** Coswick 的来信（开场）：「速来 Cambridge 区，Bouverie 街 18 号。有事相商。」——触发玩家行动
- [x] **C-02** Coswick 本人（虚弱苍白）：「夜里被一只看不见的手掐着醒来。」   ← [x] 表示该线索已发现（台账初始态）
```

规则：

- 每行：`-`（或 `*`）+ 空格 + `[ ]` / `[x]` + 空格 + `**C-XX**`（粗体编号，字母数字/连字符）+ 空格 + 线索正文。
- 编号格式：`C-01`（推荐）或 `C01`；编号用于线索台账（`clue_ledger` 表）与获得/解锁（`state_apply` `clue_id` 引用）。
- **条目边界**：正文延续到下一个 `- [ ] **C-` 条目、或 `#`（1–6 级）标题行、或文末为止（v1.1：程序以 `##`/`###` 等标题行截断正文，标题行不并入任何条目——可用 `##` 小节分组，安全）。
- **多行/嵌套内容**并入同一条（正则在条目边界内保留换行）；**不要用 `## C01 · 标题` + 字段列表的旧版格式**（不会被解析，v1.1 修正：早期文档示例与程序不符，以本格式为准）。
- 文件缺失 → 台账为空，不影响运行。

> **程序现状（v1.1 核对）**：建团时 `list_clues` 解析 clues.md 生成每局**线索台账副本**（`init_clue_ledger`）；获得线索经 `state_apply` 解锁（记录时间/获得者）；每轮管线把台账格式化为 `[C-01] [已获得] 文案…` 注入守密人上下文（KP 视角，绝不进玩家视图）；管理员可经 `/api/dev/games/{key}/clues` 查询。

### 3.5 `npcs.json` / `monsters.json`

```json
{
  "id": "shen-kecheng",
  "name": "沈珂成",
  "public": {"appearance": "俊朗年轻人，挽起袖子", "behavior": "热情好客", "lines": ["等你很久了。"]},
  "hidden": {"true_identity": "谢尔顿的伪装", "stats": {"str": 60, "con": 70}}
}
```

- `public` → 玩家视图 / 叙事可用；`hidden` → 只进 AI 上下文与开发者监视接口。

> ⚠️ **程序现状（v1.1 核对）**：`npcs.json` / `monsters.json` **当前不被程序读取**（`server/` 无消费代码），属于拆解归档 + 人工参考 + 未来扩展（与世界书 §8 同构）。AI 侧实际见到的 NPC 信息来自两个真实入口：
> 1. `scenes.json` 场景的 `npcs` / `monsters` 数组（NPC id 索引），随场景对象整体注入裁判/叙事上下文（§4）；
> 2. `kp-notes.md` / 剧本内嵌描述（§3.3）。
> 因此若希望 AI 掌握某 NPC 关键信息，应把要点写进对应场景条目的 `npcs`（id + 描述）或 kp-notes；单独拆 `npcs.json` 不产生运行时效果（保留格式供未来启用）。

### 3.6 `scenes.json`（★ 新增：场景结构化）

```json
{
  "scenes": [
    {
      "id": "s01",
      "name": "抵达园区",
      "location": "秋林苑门口",
      "summary": "出租车驶入，铁艺大门，保安室，原木色别墅",
      "checks": [
        {"kind": "skill", "skill": "知识", "target": 50, "note": "建筑风格"},
        {"kind": "psychology", "note": "观察沈珂成"}
      ],
      "clues": ["C01"],
      "npcs": ["shen-kecheng"],
      "handouts": ["cover.jpeg", "maps/qiulin-park-map.jpeg"],
      "next": ["s02"]
    }
  ]
}
```

**AI 读取模式**：`room.json`（`games` 表）记录 `current_scene`；每轮管线把**当前场景对象整体**（`json.dumps(scene)`，含 id/name/location/summary/checks/clues/npcs/handouts/next 及任意自定义字段）注入裁判与叙事阶段的 LLM 上下文，并展示 `handouts` 附件给玩家。场景切换（`state_apply` 的 `scene` 类型状态变更）按场景 **id 或 name** 查找（`modules.find_scene`）。**不需要 AI 通读全文**。

> **程序契约（v1.1 核对）**：
> - `get_scenes` 按 `meta.scene_flow` 顺序返回（未列入 flow 的场景补在末尾）；`scene_flow` 为空则按 scenes.json 原序。
> - 建团开局取 `scene_flow[0]` 或 scenes[0] 为首场景（生成开场 scene 消息 + `current_scene`）。
> - 每个场景**必须有 `id`**（程序校验）；`name` 用于场景切换按名查找（可选但推荐）。
> - `checks`：裁判阶段的场景提示（`kind: skill/sanity/luck/none`，供 AI 参考，不强制）；`clues`：场景关联线索编号；`npcs`：场景 NPC id 列表；`handouts`：附件相对路径（经 `/api/modules/{id}/handouts/{path}` 服务，防路径穿越）；`next`：后继场景（AI 调度参考，程序不强制）。

### 3.7 `handouts/`（图片附件，按用途分类）

```
handouts/
├── cover/        # 封面 / 氛围图
├── portraits/    # 角色立绘（NPC / 玩家）
├── maps/         # 地图（园区 / 楼层 / 区域）
├── items/        # 道具图（信件 / 符咒 / 机关）
└── kp-tips/      # 守密人提示图（只进 AI 上下文，不展示给玩家）
```

每张图在 `scenes.json` 或 `meta.json` 中声明用途（何时展示、给谁看、是否 kp-only）。

## 4. AI 读取模式（三种注入 · v1.1 对照实测修订）

> 下表为 2026-09-01 核对 `api/games.py::_inject_opening` + `gm/pipeline.py::run_round` + `gm/prompts.py` 后的**真实行为**（早期版本称「meta + plot 摘要开局注入」与程序不符，已更正）。

| 模式 | 实际内容 | 时机 |
|---|---|---|
| **开局注入** | ① `scenes.json` 首场景 → 玩家可见的开场 scene 消息 + `current_scene`；② `kp-notes.md` **全文** → 该局 `kp_notes` 表（round 0）；③ `clues.md` → 线索台账副本（`init_clue_ledger`）。**不含** meta.json / plot.md | 创建游戏 / 开局 |
| **场景注入** | `scenes.json` 当前场景对象**整体**（id/name/location/summary/checks/clues/npcs/handouts/next/自定义字段）→ 裁判与叙事阶段 LLM 上下文 | 每轮管线（读取 `current_scene`）|
| **运行时 KP 上下文** | ④ `kp_notes` 表尾部（最近 10 条：开局原文 + 每轮 `private_notes`）+ ⑤ **线索台账**（`[C-01] [已获得/未获得] 文案…`，`pipeline.py::_format_clue_ledger`）→ 守密人上下文 | 每轮管线 |
| **按需检索** | `pregens/`（建卡页展示与一键使用）、`handouts/`（场景附件渲染于叙事流，经 `/api/modules/{id}/handouts/{path}`，防穿越） | 运行时按需 |
| **不注入** | `plot.md`、`npcs.json`、`monsters.json`（v1.1 确认程序未消费，见 §3.2/§3.5） | — |

> 所有「KP 侧」内容（kp_notes 表 / 线索台账 / private_notes）**只进 AI 上下文，绝不进玩家视图**——SSE 公共流、公共视图、消息表均不含（隐私铁律，M2 §8 与 M7 线索台账设计共同保证）。

## 5. 拆解步骤（源材料 → 模组包）

1. **通读源材料**（PDF / 文本+图片），识别：背景、场景流程、检定、线索、NPC、怪物、附件图片。
2. **分文件**：按 §3 规范写入 `plot.md` / `kp-notes.md` / `clues.md` / `npcs.json` / `monsters.json` / `scenes.json`。
3. **图片分类**：从 PDF 提取插图，按用途放入 `handouts/` 分类目录（jpg/png/webp，单张 ≤ 10MB）。
4. **预制角色**：如有，转成角色卡 JSON 放入 `pregens/`。
5. **校验**：跑 §6 校验清单。
6. **登记**：`number` 递增，`/api/modules` 自动收录（扫描 `modules/` 目录）。

## 6. 校验清单

> 程序内置校验见 `server/modules.py::validate_module`（meta 必填字段 / files 存在 / scenes.json 为数组 / scene_flow 覆盖 / 场景含 id）——`/api/dev/...` 之外测试与开发期可直调。以下为拆解人工清单：

- [ ] `meta.json` 合法 JSON，`schema == "trpg-module/v1"`，必填字段齐全（id/number/cn/system/summary/files）
- [ ] `files` 中声明的每个文件/目录实际存在
- [ ] `plot.md` / `kp-notes.md` / `clues.md` 为 UTF-8 Markdown
- [ ] **`clues.md` 每条目为程序可解析格式**：`- [ ] **C-XX** 线索正文…`（v1.1 新增；旧版 `## C01 · 标题` 字段列表格式**不会被解析**）
- [ ] `scenes.json` 合法 JSON 且为 `{"scenes": [...]}`；**每个场景含 `id`**；`meta.scene_flow` 中的 id 均存在于 scenes（程序校验）
- [ ] `npcs.json` / `monsters.json` / `plot.md`：合法 UTF-8（可选，**当前程序不读取**，见 §3.2/§3.5）
- [ ] `handouts/` 图片格式合法（jpg/png/webp），`scenes.json` 引用的附件存在（服务端经 `/api/modules/{id}/handouts/{path}` 返回，防路径穿越）
- [ ] `kp-notes.md` 与 `plot.md` 无交叉泄漏（真相只出现在 kp-notes）
- [ ] 原版 PDF 等授权材料**不入库**（放 `archive/模组/` 或本地），模组包内只放拆解产物

### 8.1 目录与格式（预留草案）

```
worlds/<world_id>/
├── meta.json          # schema: trpg-world/v1 → id/name/cn/system/summary/tags/files
├── npcs.json          # NPC 条目（id / 关键词 / public / hidden）
├── locations.json     # 地点条目（id / 关键词 / 描述 / handouts）
├── items.json         # 物品条目（id / 关键词 / 效果）
├── events.json        # 事件条目（id / 关键词 / 触发 / 后果）
└── readme.md          # 来源与授权（可选）
```

每条目统一结构（以关键词驱动注入）：

```json
{
  "id": "npc-shen-kecheng",
  "name": "沈珂成",
  "keywords": ["沈珂成", "房东", "表哥"],
  "tags": ["npc", "主线"],
  "public": {"appearance": "俊朗年轻人，挽起袖子", "behavior": "热情好客", "lines": ["等你很久了。"]},
  "hidden": {"true_identity": "谢尔顿的伪装", "stats": {"STR": 60}}
}
```

### 8.2 阅读逻辑（预留）

1. **开局注入**：meta 摘要 + 全部 `public` 字段（世界基调）/ `hidden` 只进 KP 上下文。
2. **按需检索**：叙事/裁判阶段按当前文本关键词命中条目 → public 进玩家视图、hidden 进 KP 上下文；未命中不注入。
3. **隐私分级**：与模组一致——`hidden` 绝不进玩家视图；kp-only 附件只进 KP 上下文。

> 实现时机：确认需要世界书后，按本格式拆第一份世界书，并在 `server/modules.py` 旁新建 `server/worlds.py`（同为目录扫描 + 结构化读取）。
