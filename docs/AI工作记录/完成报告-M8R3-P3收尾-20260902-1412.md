### T-A12 · `Admin.vue` 资源按钮 loading 拆 7（P2，二次复核追加必修）

**文件**：`frontend/src/views/Admin.vue`

```ts
// :24 类型由布尔改为「当前正在查哪个 key」
const loadingResource = ref<DevResource | null>(null)

// onResource（:71-89）
async function onResource(res: DevResource): Promise<void> {
  if (!gameKey.value.trim()) { message.warning('请输入游戏号'); return }
  loadingResource.value = res          // 同步置为当前 key，再 await
  try { resourceData.value = await getDevResource(gameKey.value.trim(), res, devToken.value.trim()) }
  catch (e) { message.error(...) }
  finally { loadingResource.value = null }  // 置 null（非 false），异常路径也解锁
}

// 模板 :136
:n-button ... :loading="loadingResource === r.key"
```

**问题复盘**：上一轮 T-A5.3 改的「`loadingResource` 单一布尔」使 `RESOURCES` 7 个按钮**全部绑定同一个 `loadingResource`** → 点任意一个，7 个一起转。本轮把状态从布尔升级为「当前查询的 key」，把「同步 spinner」降级为「按 key 隔离」。

**CDP 断言**（`ta12-resource-loading`，Edge headless，注入 `rg_dev_token` + 填 `gameKey=6956a75b` 后点「叙事流消息」）：

```json
{"enabledAtClick": true, "maxLoading": 1, "loadingLabels": "叙事流消息"}
```

- `enabledAtClick:true` → 按钮在点击时 enabled（`devAuthed && gameKey` 闸门工作）。
- `maxLoading:1` → 点击瞬间最多只有 **1 个** 资源按钮转圈（旧 bug 是 7 个同时转，`maxLoading` 会是 7）。
- `loadingLabels:"叙事流消息"` → 转的那个正是被点的按钮，其余 6 个**不带** `n-button--loading`。

✅ 隔离生效。点一个只转一个。

> **验证方法说明**：首次 CDP 轮询（25ms 间隔 × 1.5s）曾误报 `maxLoading:0`——原因是无效 `devToken` 下接口往返 <25ms，spinner 在两次采样点之间就消失。复测时通过注入层把 `/dev/*` 接口人为延迟 450ms 制造确定窗口，再以 20ms 密集轮询，稳定捕捉到 `maxLoading:1`。该误报属采样时机问题，**非代码缺陷**。

### pytest 86 passed / 5 failed —— 非本轮回归，说明如下

- **失败的 5 个**全部是 `_start_live_server` 系列 SSE 端到端测试（在测试内起真实 uvicorn + 真实 HTTP 调用）：`test_api.py ×2`、`test_m4.py ×1`、`test_m5.py ×1`、`test_m7.py ×1`。
- **根因**：这些测试请求 `/api/games/{key}/join`，该路由真实存在（`server/api/games.py:182` `@router.post("/{game_key}/join")` + `games.router` 前缀 `/games` + `include_router(prefix="/api")` → 实际 `/api/games/{key}/join`）。**in-process `TestClient` 打同一路径返回 200 JSON**，但**真实 uvicorn（HTTP）上下文下该嵌套路由未被匹配**，返回 404 `{"detail":"Not Found"}`（当 `frontend/dist` 存在时则被 SPA 静态挂载兜底为 `index.html`，表现为 `JSONDecodeError`）。
- **这是环境/版本差异，不是代码回归**：本轮只改了 `frontend/src/**`，`server/` 字节未变。重跑前需重建 venv（上一会话的 venv 已被清理），钉 `fastapi==0.115.6 / starlette==0.41.3 / pydantic==2.9.2 / httpx==0.27.2` 并补装 `openai`（测 `test_llm_limit` 需要）后，除这 5 个 live-SSE 测试外全部 91-5=86 通过；in-process 的 API/engine/store/schema 测试均通过，证明后端逻辑未被本轮改动影响。
- **建议**：这 5 个 live-SSE 测试的失败与任务书范围（前端体验修复）无关，属测试基建对运行环境的耦合，建议作为独立技术债由 E3n 裁决是否修复（例如让 live 测试复用与 in-process 相同的路由解析，或在前端构建产物存在时排除 SPA 挂载干扰）。**本轮不修改 `server/`，遵守红线。**
