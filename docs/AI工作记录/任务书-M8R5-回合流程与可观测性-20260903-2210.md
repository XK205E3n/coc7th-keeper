## 0. 本轮定位 —— 与以往轮次的**关键区别**

前几轮只改 `frontend/src/**`。**本轮 E3n 已授权动 `server/`**（实测暴露的问题大多在后端流程与可观测性），允许的 server 文件范围见 §5 红线。这是红线变化，务必逐字阅读。

### 0.1 实测暴露的问题（全部有数据库证据，勿再重复诊断）

E3n 用 `7d14a688` 房公网实测（2 玩家 + 手机蜂窝 + cloudflared）：

1. **强制推进空转丢行动**：`POST /api/games/{key}/advance` 是**纯 round+1**（`games.py:480-490`，注释自述「轮次 +1」）。实测 round=3 房主提交了行动、乔治未提交，房主按强制推进 → round 跳到 6，**round 3 已提交的行动被静默丢弃**（仍留在 actions 表但新回合不消费），且无任何 LLM 结算（llm_log 证实 round 3-6 零调用）。
2. **状态黑盒**：phase=collecting 时前端不显示「在等谁提交」，玩家不知道房间为什么不动。`players.has_submitted` 数据已存在且已随 action_received 广播，**纯前端展示缺口**。
3. **LLM 状态不可见**：`run_round` 结算期间（数十秒）前端无任何「AI 结算中」指示；llm_log 有数据但只在事后管理页可看。
4. **无删除房间手段**：无 DELETE 端点，测试房堆积（data/games/ 已 40+ 个 db）。
5. **玩家行动无回显**：提交后只变 ✅ 布尔，玩家看不到自己提交了什么文本。
6. **进站无门禁**：`config.access_password` 为占位字段（服务端/前端 0 消费），公网暴露后首页完全开放。

### 0.2 必须先理解的现有机制（读 `server/api/games.py` 确认，不要凭本任务书想象）

- **自动结算已存在**：`_maybe_auto_advance`（games.py:373）—— 活跃玩家全部提交 → `run_round`（裁判 → 引擎掷骰 → 叙事 → 落库）→ `advance_game`。实测 round 0/2 正常跑通（llm_log 4 次调用全 ok）。
- **强制推进**：`advance` 端点（games.py:480）—— 纯跳号。
- **二者关系**：全员提交是自动的，无需按钮；**缺的是"有人不提交时房主怎么办"** —— 这就是本轮 T-E2 的核心。

### T-E2 · 强制推进语义修复（本轮核心，先出方案再动手）

**现状**：`advance` 纯跳号，丢弃已提交行动。

**目标语义**（E3n 原案 + 约束）：
- 强制推进 = **房主放弃等待，立即以当前已提交的行动结算本轮**。未提交的活跃玩家按「本轮无行动」参与裁判（或被跳过个人回合，二选一，**在完成报告里说明你选了哪种、为什么**）。
- **已提交的行动绝不允许静默丢弃** —— 这是硬约束。
- 结算复用现有 `run_round` 管线（`_maybe_auto_advance` 锁内那段逻辑），**抽成共享函数**，不要复制粘贴两份。
- 前端：强制推进前弹确认框，明确列出「将跳过：乔治」。
- 自动结算行为**保持不变**。

**实现提示**：把 `_maybe_auto_advance` 锁内那段抽成 `async def _settle_and_advance(request, game_key, skip_missing: bool)`；`advance` 端点与 `_maybe_auto_advance` 都调它。

**DoD**：
- pytest：现有 91 项全过 + 新增用例（强制推进时未提交玩家被跳过、已提交行动进入裁判、round 正确 +1）
- 实测脚本：模拟 2 人房 1 人提交 → 强制推进 → 叙事产出且未提交者被跳过

### T-E3 · LLM 结算状态实时指示

- `run_round` 开始/结束时广播 `llm_started` / `llm_finished`（payload：round、stage；失败带 error 摘要）。`run_round` 在 `server/services/` 或 `server/roundman.py`（先 grep 确认实际位置），事件经现有 `bus.publish`。
- 前端叙事区：结算期间显示「AI 结算中…」指示（复用现有 loading 样式）；`llm_finished` 带失败信息时在叙事区显示可读错误（现在失败 = 无声，正是「卡住不知道什么状态」的另一半原因）。

**DoD**：CDP 或 API 断言 —— 提交行动后能观察到 llm_started（可 mock LLM 延迟）；失败时前端显示错误而非无声。

---

### T-E4 · 删除房间

- 后端：`DELETE /api/games/{game_key}`（需 X-Host-Token）。语义：**软关闭** —— 置 phase=closed 并广播 `room_closed`，把 db 文件改名归档（如 `<key>.closed.db`）而非物理删除（保守优先，物理清理留给后续管理页）。
- 前端：房主面板「删除房间」按钮 → 确认弹窗要求**输入游戏号**才能确认 → 成功后跳回首页。
- 所有在线玩家收到 `room_closed` → 弹提示并跳首页。

**DoD**：pytest 新用例（非房主 403、房主成功、关闭后 join 返回房间已关闭）；前端 CDP 确认二次确认框工作。

---

### T-E5 · 玩家行动回显

- 玩家提交后，在自己面板显示本轮已提交的行动文本（`action_version` 变更时更新）。数据源：提交时本地已有文本 + 刷新后可从服务端恢复（actions 表有数据；如有现成端点用现成的，没有就在 `GET /api/games/{key}` 的视图里带上自己的本轮行动文本）。

**DoD**：CDP —— 提交「观察四周」后页面显示「已提交：观察四周」；刷新后仍在。

---

### T-E6 · 进站全局门禁（E3n 点名）

- 让 `config.access_password` 真正生效：
  - 服务端：中间件或入口校验 —— 未认证请求访问**页面与房间 API** 时要求密码；`/api/health` 豁免。
  - 前端：未认证时显示密码门（输入框），提交后存 localStorage，后续请求带 `X-Access-Token` 头（或 cookie，选一种并在报告说明理由）。
  - **与房间级密码（M5）语义区分**：站点门禁管「能不能看到这个站」，房间密码管「能不能加入这个房」。两者可叠加。
  - `access_password` 为 null/空 → 门禁关闭，行为与现在完全一致（向后兼容）。

**DoD**：pytest 新用例（未设密码时全放行；设了密码后无 token 访问房间 API 401、带正确 token 200、health 豁免）；前端 CDP 密码门流程。
