## §1 T-B1 · 建卡 API 服务端 schema 校验影响面

### 1.1 现状与漏洞定位

建卡端点：**`server/api/games.py:255-273` `create_character`**

```python
@router.post("/{game_key}/characters")
async def create_character(game_key: str, body: CharacterBody, request: Request) -> dict:
    st, game = _room_or_404(game_key)
    player = player_from_token(request, game_key)
    if body.character is not None:
        char = body.character          # ← 直接采用前端传来的 dict，无任何 schema 校验
        char_name = body.name or player["name"]
    elif body.action == "auto":
        char_name = body.name or player["name"]
        char = build_character(char_name)
    else:
        raise HTTPException(status_code=400, detail="需提供 character（角色卡 JSON）或 action=auto")
    st.set_character(game_key, player["uid"], char_name, char)   # ← 原样落库
```

入参模型：**`server/api/games.py:90-94`**

```python
class CharacterBody(BaseModel):
    action: str | None = None
    name: str | None = None
    character: dict | None = None      # ← 仅声明为 dict，不校验内部字段
```

落库：**`server/store.py:384-392` `set_character`** —— 仅 `json.dumps` 后 `INSERT`，**无校验**。

**结论（漏洞）**：`character` 字段是裸 `dict`，绕过前端直打 `POST /api/games/{key}/characters` 可写入任意非法角色卡（缺字段、字段类型错误、属性值超出 0–100、技能名乱写等），服务端不拦截。前端当前的唯一校验在 `frontend/src/views/Characters.vue:69-86`（`schema` 字符串检查 + 角色名非空 + 一个不拦截的 SAN 提示），属**纯前端校验**，可被绕过。

### 1.2 校验放哪一层

| 方案 | 位置 | 评估 |
|---|---|---|
| A. 新增 Pydantic 模型（推荐） | 在 `server/api/games.py:90` 附近新增 `CharacterCreate`（或把 `CharacterBody.character` 从 `dict` 改为该模型） | 声明式、自动返回 422、可复用、最少手写代码。**推荐**。 |
| B. 路由内手写校验 | 在 `create_character`（`games.py:255`）函数体内 `if/raise`（仿 `games.py:307` 风格） | 可行，但要手写每条规则、易漏；与 FastAPI 风格不一致。 |
| C. 复用 `server/engine` | 在 `server/engine/build.py` 的 `build_character` 内加校验 | **不合适**：`build_character`（`build.py:94-111`）的职责是「自动生成」一张新卡，并不消费外部传入的卡；它当前**不做任何校验**（仅生成）。把入参校验塞进生成函数会污染职责。可在 engine 新增一个独立的 `validate_character()` 归一化函数，由路由调用，但模型本身仍应在 API 层。 |

`build_character` 是否会「顺带校验」：**不会**。`build.py:94-111` 只返回固定结构（schema/name/meta/attributes/derived/skills=DEFAULT_SKILLS/inventory/notes/sanity），对传入数据零检查。

**建议**：方案 A —— 在 API 层新增 `CharacterCreate` Pydantic 模型，仅约束「形状」与「取值范围」，把 `state/sanity/derived/meta/notes/inventory` 设为可选并给默认值（见 1.4 风险）。

### 1.3 失败状态码：建议 422（说明理由）

- 现有代码对「业务规则错误」统一用 `raise HTTPException(status_code=400, detail=...)`（见 `games.py:131,246,268,307`、`store`/`roundman` 多处）。
- 但 **FastAPI 对 Pydantic 模型校验失败默认返回 `422 Unprocessable Entity`**（语义：请求体格式/字段非法）。
- 本次是**字段级 schema 校验**（类型、取值、必填字段缺失），按 HTTP 语义与 FastAPI 约定应返回 **422**；若改用方案 B 手写校验，则为与现有风格一致可继续用 **400**。
- **裁决建议**：采用方案 A（Pydantic）时直接用 422（零额外代码、标准、前端 `Characters.vue` 的 `buildCharacter` 已能接住非 2xx 报错）。无需刻意改成 400 去「对齐」——400 与 422 在前端 `catch` 处理上无差异（均走 `message.error`）。**结论：422 优先；若 E3n 强求全局风格统一，则用 400。**

### 1.4 是否破坏 9 张预置卡 —— ⚠️ 高风险点

**预置卡入库路径与建卡端点是否同一路径？——是，同一端点。**

- 预置卡读取：`server/modules.py:121-130` `list_pregens` 读取 `modules/*/pregens/*.json`。
- 前端消费：`frontend/src/views/Characters.vue:165-176` `usePregen(pregen)` → `await buildCharacter(gameKey, { character: pregen, name })`。
- `buildCharacter` 客户端：`frontend/src/api/client.ts:204-209` → `POST /games/${key}/characters`。
- 即：**预置卡也走 `create_character`（`games.py:255`）**，与手动/粘贴建卡同端点。

**预置卡能否通过严格校验？——若校验要求 `state` 字段，则 9/9 全部失败。**

用脚本对 9 张预置卡做最小 schema 校验（仅检查 `schema==coc7-character/v1`、9 项属性齐全、skills 为 dict、以及可选字段是否存在），结果：

```
[FAIL] sleeping-cat/adult-misaki.json:      missing_optional:state
[FAIL] sleeping-cat/teen-haru.json:         missing_optional:state
[FAIL] sleeping-cat/teen-shizuku.json:      missing_optional:state
[FAIL] the-haunting/delphine-mcquire.json:  missing_optional:state
[FAIL] the-haunting/theron-quist.json:      missing_optional:state
[FAIL] toy-dancer-comes/relay.json:         missing_optional:state
[FAIL] yuren-pie/foreign-student.json:      missing_optional:state
[FAIL] yuren-pie/nerd.json:                 missing_optional:state
[FAIL] yuren-pie/old-money.json:            missing_optional:state
```

- 9 张卡 **都缺少 `state` 字段**（但都含 `schema`/`attributes`(9 项)/`derived`/`sanity`/`meta`/`inventory`/`notes`/`skills`）。
- 额外佐证：预置卡本身已含**模板之外的技能键**（`Photography`、`Science(Biology)`、`Language(Japanese)`、`Language(Chinese)`、`Language(Other)` 等），说明引擎对技能键**本就不强制白名单**（与 §2.3 一致）。

**客户端三条路径对字段完整度的差异（决定校验必须「宽松」）：**

| 路径 | 发送字段 | 缺什么 |
|---|---|---|
| 预置卡 `usePregen` | schema/name(经 body)/attributes/derived/sanity/meta/inventory/notes/skills | **无 `state`** |
| 手动 `onManual`（`Characters.vue:206-213`） | schema/name/attributes(仅填了的)/derived:{}/skills:{}/inventory:[] | **无 meta/sanity/state/notes、derived 空、属性不全** |
| 粘贴 `onPasteUpload`（`Characters.vue:55-99`） | 完整 JSON（通常含全部字段） | 取决于用户 |

**结论**：服务端校验模型必须把 `state`、`derived`、`sanity`、`meta`、`notes` 设为 **Optional + 服务端默认值**（缺失时由 `create_character` 或服务端 `validate_character()` 自动补默认 `state`：`{hp,max_hp,san,max_san,clues:[],conditions:[],gold:0}`）。若把 `state` 设为必填，9 张预置卡 + 手动建卡全部被拒，**破坏现有建卡流程**。属性/技能只校验「类型与 0–100 取值」，**不要求 9 项属性全填**（手动路径只填部分）。

### 1.5 是否破坏前端建卡流程

- 前端四路径（预置/AI 草稿/手动/粘贴）最终都经 `buildCharacter` → `POST /games/{key}/characters`（`client.ts:204`）。
- 只要服务端校验按 1.4 设为「宽松可选 + 取值/类型校验」，前端**合法请求不会被误拒**：
  - 预置卡：schema 对、属性齐、skills 为 dict → 通过（仅 state 缺失由服务端补）。
  - 手动：schema 对、attributes 为 int、skills 为 dict（空也行）→ 通过。
  - 粘贴：前端已自检 schema（`Characters.vue:69`），与服务端规则一致 → 通过。
  - AI 草稿：`action=auto` 分支走 `build_character`，根本不进 `character` 校验分支 → 不受影响。
- **唯一新增失败场景**：用户粘贴非法 JSON（类型错、属性超 100）时被服务端拒——这正是 T-B1 要补的能力，属预期行为，不破坏流程。

**T-B1 改动文件清单（供下一轮实现，本次未改）：**
1. `server/api/games.py:90-94` 附近：新增 `CharacterCreate` Pydantic 模型（把 `CharacterBody.character: dict` 改为该模型，或将校验逻辑加在 `create_character` 内）。
2. `server/api/games.py:255-273` `create_character`：对 `body.character` 走校验；对缺失的 `state/derived/sanity` 给默认值。
3. （可选）`server/engine/build.py` 新增 `validate_character()` 归一化函数供路由复用——**注意 `build_character` 本身不校验入参，不要在其中塞校验**。
4. 测试：在 `server/tests/test_api.py` 增加「直打 API 写非法卡被 422/400 拒」「预置卡/手动卡仍可通过」用例。当前 `pytest --collect-only` 共 91 个测试可正常收集（`server/tests/*` 收集通过），新增用例不影响现有收集。

## §3 综合结论与建议（供 E3n 裁决）

### 3.1 可下一轮直接做的低风险改动（建议直接批准）
- **T-B2 模板加 `Computer Use`**：改 `templates/character-sheet-template.json`（`:27-74` 技能段）加一项 `"Computer Use": 5`。对 `server/engine`、9 预置卡、现有测试 **零影响**（证据 §2.3）。前端 `GROUP_KEYWORDS` 已能分组（§2.4）。**纯文档/底稿改动，风险极低。**
- **T-B2 前端 `CN_TO_EN` 映射调整**：按方案 X 或 Y 改 `CharacterSheet.vue:118-132` 一处（§2.4）。注意与 T-A1 权宜映射的取舍，属产品决策但改动面极小。
- 可选：同步 `server/engine/build.py:80-91` `DEFAULT_SKILLS` 加 `"Computer Use": 5`，让 auto 卡也带（§2.5），无风险。

### 3.2 需 E3n 裁决的中风险改动
- **T-B1 服务端 schema 校验**：必须新增加 `CharacterCreate` 模型（`games.py:90` 附近）+ 在 `create_character`（`games.py:255`）对 `state/derived/sanity/meta/notes` 给默认值（§1.4）。**核心裁决点**：校验宽松度——若把 `state` 设必填，9 张预置卡 + 手动建卡全挂。建议 E3n 确认「缺失可选字段服务端补默认」策略，再放行实现。
- **状态码 422 vs 400**：建议 422（Pydantic 默认、语义正确），若要求与现有 400 风格统一则改 400（§1.3）。需 E3n 定调。
- **9 张预置卡是否逐卡补 Computer Use / Hide**：按 §2.2 表格，现代背景模组（sleeping-cat / toy-dancer-comes / yuren-pie）相关卡建议补，1920s 的 the-haunting 两张不建议。属内容决策，建议 E3n 拍板后由内容轮逐卡编辑 `modules/*/pregens/*.json`。

### 3.3 不建议做的事
- 不要把入参校验塞进 `build_character`（`build.py:94`，其职责是生成非校验，§1.2）。
- 不要对预置卡/手动路径设 `state` 或「9 项属性全填」为必填（§1.4 会破坏现有流程）。
- 不要为 Computer Use 新建分组（已有「学术」组关键词覆盖，§2.4）。
